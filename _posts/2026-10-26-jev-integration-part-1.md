> 전편은 Jev 연동 구조와 제약사항을 다룬다. 실제 응답 시간·정확도·비용 비교는 측정 후 후편에서 다룰 예정이다. 이 글에 실측 성능 결과는 없다.

풋살 경기 기록 서비스 ‘모두의 심판’에서는 사용자가 말이나 글로 득점을 기록한다. “창명이 어시, 민수 골, 12분”이라고 입력하면 모델이 선수와 시간을 해석하고, 사용자가 미리보기를 확인한 뒤 저장한다. 음성은 Soniox가 텍스트로 변환하고, 그다음 OpenAI `gpt-4.1-mini`가 기록을 해석한다.

이번에는 이 해석 단계에 TypeSafe의 Jev를 연결했다. 목표는 실제 경기 기록에서 두 모델의 응답 속도와 정확도를 비교할 수 있는 환경을 만드는 것이었다. 하지만 시작부터 단순한 API 교체로 끝나지 않았다.

## JSON을 생성하는 모델에서 선택하는 모델로

기존 경로에서는 모델이 골 목록, 선수 이름 원문, 불확실한 내용에 대한 설명을 JSON으로 만들어준다. 반면 Jev는 상태와 질문을 전달하면 선택·점수·참 여부에 대한 답을 반환하는 방식이다. 이 연동에서는 Choice와 Noul을 사용했다. [TypeSafe 시작 가이드](https://docs.typesafe.ai/introduction/quickstart)

우리 서비스에 맞추면 질문은 다음처럼 바뀐다.

- 우리 팀의 골이 몇 개인가?
- 첫 번째 골의 득점자는 명단 중 누구인가?
- 어시스트가 있는가? 있다면 누구인가?
- 기존 기록 중 취소해야 할 골이 있는가?

이 답을 기존 미리보기 형식으로 조립하는 일은 서버가 맡는다. 같은 결과 형식을 사용하더라도, 그 결과를 만드는 과정은 달라진다.

## 모델의 제약과 구현의 제약을 구분하기

Jev가 자유로운 골 배열을 직접 생성하지 않는다고 해서 애플리케이션이 배열을 만들 수 없는 것은 아니다. 여러 번 질문하거나 후보를 추출하는 방법도 있다. 이번 구현은 한 번의 요청에 고정된 골 슬롯을 준비하는 방식을 선택했다.

| 항목 | 이번 어댑터의 처리 범위 |
|---|---|
| 한 번에 분석하는 득점 | 우리 팀 3골, 상대 팀 3골까지 |
| 득점 시간 | 0~120분 또는 모름 |
| 취소·정정 대상 | 기존 유효 골 중 최근 10골 |
| 입력에 나온 이름 원문 | 반환하지 않음 |
| 명단에 없는 이름 | 존재 여부를 경고하지만 이름 원문은 반환하지 않음 |
| 자유로운 설명 | 모델 설명 대신 서버가 만든 경고를 별도로 표시 |

앞의 세 가지는 이번 구현에서 정한 범위다. Jev가 원천적으로 네 골이나 121분을 다룰 수 없다는 뜻은 아니다. 범위를 늘리면 질문 구성, 토큰 사용량과 결과 검증도 달라지므로 별도 평가가 필요하다.

현재는 슬롯을 초과하면 범위 안의 결과와 경고를 반환한다. 따라서 HTTP 응답이 성공했다고 입력 전체를 처리한 것은 아니다. 사용자는 경고와 미리보기를 확인해야 하며, 비교할 때도 이를 완전한 정답으로 세면 안 된다.

이름 원문도 중요한 차이였다. 사용자가 “민수형”이라고 말했는데 명단의 “김민수”를 원문 필드에 넣으면, 실제 발화를 보존한 것처럼 보인다. 이번 어댑터에서는 그 칸을 비워두었다. 별도 원문 추출 로직을 만들 가능성과, 현재 기능이 제공하지 않는다는 사실을 구분하기 위해서다.

## 확률이 있어도 정답이 보장되지는 않는다

Jev의 Choice 응답에는 선택지별 확률과 confidence가 있다. [Choice 문서](https://docs.typesafe.ai/primitives/choice)

이번 구현은 선수 선택 확률이 낮으면 확정하지 않고 후보를 미리보기에 넘긴다. 코드의 확정 기준은 0.6, 후보 기준은 0.2다. 이 값은 아직 실측으로 보정하지 않은 초기 설정이다. confidence와 선택지 확률을 같은 값으로 취급하거나, 0.6을 곧바로 한국어 입력에서의 정답률 60%로 해석해서는 안 된다.

모델이 구조에 맞는 응답을 주는 것과 경기 기록을 맞게 이해하는 것은 별개다. 선수 ID, 취소할 골, 팀 권한은 기존과 같이 서버가 검증한다. 결과를 바로 저장하지 않는 원칙도 유지했다.

## 관리자 본인에게만 적용하는 실험

일반 사용자까지 한꺼번에 모델을 전환하지 않고, 백오피스에서 관리자 본인이 사용할 제공자를 선택하도록 했다. 선택값은 계정에 저장한다.

- 미선택: 서버의 기본 제공자 사용
- OpenAI: OpenAI 명시 선택
- TypeSafe: Jev 명시 선택

매 분석 요청에서 관리자 여부를 다시 확인한다. 권한을 회수한 계정에 선택값이 남아 있어도 서버 기본 제공자를 사용한다. 관리자 권한과 Jev 선택값을 묶는 DB 제약을 두지 않은 이유도 있다. 실험 설정이 남았다는 이유로 관리자 권한 회수가 실패해서는 안 되기 때문이다.

이 권한은 모델 선택에만 적용된다. 관리자가 다른 팀의 경기 기록에 접근할 수 있도록 팀 멤버 검사를 생략하지 않는다.

## 비교를 위해 실패를 드러내기

Jev가 실패했을 때 OpenAI로 자동 전환하면 기록을 완료할 가능성은 높아진다. 하지만 이번 실험에서는 Jev가 어디서 실패하는지 관찰해야 한다. 따라서 자동 fallback 없이 관리자가 모델을 바꾸어 재분석하게 했다.

미지원 입력도 별도로 남긴다. 사용자에게 결과와 경고를 반환하더라도 사용량 기록에는 미지원 코드와 함께 성공이 아닌 상태로 남긴다. 집계할 때는 통신 오류와 기능 미지원을 나눠 봐야 한다. 둘은 해결 방법이 다르기 때문이다.

## 속도를 비교하려면 측정 경계를 먼저 정해야 한다

사용자가 기다린 시간에는 브라우저와 서버 사이 통신, 음성 업로드, STT, 모델 호출, 서버 검증과 미리보기 조립이 섞여 있다. 모델 교체 효과를 보려면 이 시간을 분리해야 한다.

현재 구조는 서버가 외부 호출을 감싸 측정한 LLM·STT 시간을 관리자에게 전달한다. 사용량 기록과 같은 측정값을 사용한다. 이 시간에는 서버와 외부 제공자 사이의 통신과 호출 내부의 대기·재시도가 포함된다. 브라우저에서 서버까지의 왕복이나 분석 전후 처리 전체를 포함하는 시간은 아니다.

STT 측정에는 제공자로의 업로드, 전사 완료를 확인하는 폴링과 결과 조회가 들어간다. 따라서 순수한 음성 인식 연산 시간이라고 부를 수 없다. 모델 호출 시간과 사용자가 미리보기를 볼 때까지의 시간은 각각 측정할 필요가 있다.

## 아직 성능 결론은 없다

현재 구현 문서에 기록된 검증은 MockWebServer 기반이다. 실제 Jev API 호출과 실측 벤치마크는 아직 실행하지 않았다. 따라서 다음 수치는 아직 없다.

| 평가 항목 | 현재 결과 |
|---|---|
| OpenAI 대비 응답 시간 중앙값·p95 | 미측정 |
| 한국어 득점자·어시스트·정정 정확도 | 미측정 |
| 실패·미지원·안전한 보류 비율 | 미측정 |
| 요청당 비용·정답당 비용 | 미측정 |

다음 단계에서는 같은 한국어 입력과 선수 명단, 기존 골 기록으로 두 모델을 비교한다. 단순 골뿐 아니라 자책골, 복수 득점, 취소·정정과 미등록 이름을 포함한다. 지원 가능한 일부 사례의 빠른 응답만으로 전체 기능을 대체할 수 있다고 결론 내리지 않을 것이다.

재시도 정책도 맞춰야 한다. 현재 기본 설정은 OpenAI와 Jev가 다르므로, 재시도 없는 모델 비교와 실제 서비스 설정의 비교를 분리할 계획이다. 실패 사례를 버리지 않고 비용과 전체 대기 시간에 포함한다.

이번에 마련한 것은 빠르다는 결론이 아니라, 그 결론을 검증할 수 있는 연결 구조다. 모델이 답하지 못하는 부분을 미리보기에 드러내고, 실제 사용한 모델과 시간을 기록해야 교체 여부를 판단할 수 있다.

## 후편에서 확인할 것

실제 API 연결이 준비되면 동일한 한국어 평가 세트로 응답 시간, 정답률, 미지원 비율과 정답당 비용을 측정한다. 후편에서는 원시 측정 조건과 결과를 함께 공개하고, 전면 교체가 가능한지 또는 제한된 입력에만 적합한지 판단할 예정이다. 후편은 아직 발행되지 않았다.
